# Роли и привилегии

Все права задаются единственной системой AccessRole → RolePrivilege → UserAccessRole. У пользователя может быть несколько ролей; отсутствие ролей означает обычный клиентский аккаунт. Поля User.role, User.userRole и enum UserRole удалены. Название роли не влияет на доступ. Управление ролями и назначениями доступно только пользователям защищённой роли с isAdministrator: true. Этот признак возвращается API, но не принимается в запросах.

## API управления ролями

Все запросы требуют Bearer JWT администратора.

| Метод и путь | Результат |
| --- | --- |
| `GET /admin/privileges` | Каталог: `key`, `description`, `scoped`, `adminOnly` |
| `GET /admin/roles` | Список ролей с привилегиями |
| `GET /admin/roles/:id` | Одна роль |
| `POST /admin/roles` | Создание, `201` |
| `PUT /admin/roles/:id` | Полная замена названия, описания и привилегий, `200` |
| `DELETE /admin/roles/:id` | Удаление неназначенной роли, `204` |
| `PUT /admin/users/:id/roles` | Полная замена пользовательских ролей аккаунта, `204` |

Пример создания роли:

```json
{
  "name": "Оператор гостиницы",
  "description": "Заказы назначенных направлений",
  "grants": [
    { "privilege": "orders.read", "scope": "assigned" },
    { "privilege": "orders.status", "scope": "assigned" },
    { "privilege": "orders.schedule", "scope": "assigned" },
    { "privilege": "calendar.read", "scope": "assigned" }
  ]
}
```

Назначение через `PUT /admin/users/42/roles`: `{"roleIds":[1,2]}`. Пустой массив снимает все роли; снять роль последнего администратора нельзя (409). roleIds также поддерживается в POST /users и PUT /users/:id, только для администратора. Роли и профиль сохраняются одной транзакцией. Отсутствие roleIds сохраняет назначения при обновлении; [] очищает их. null недопустим. serviceTypeIds задаются через те же запросы независимо от названий ролей.

`grants` обязателен, пустой массив допустим. Повторять ключ нельзя. Название обрезается по краям, обязательно, до 100 символов; уникальность без учёта регистра. Описание необязательно, до 1000 символов; отсутствие в PUT очищает его. Неизвестные поля, ключи, области и повторяющиеся идентификаторы дают `400`. Несуществующие роли/пользователи — `404`; занятое название или удаление назначенной роли — `409`. Перед удалением снимите роль со всех пользователей.

## Области действия

- `all`: операция доступна для всех соответствующих ресурсов.
- `assigned`: операция ограничена направлениями из `serviceAssignments`; без назначений доступных направлений нет.

`assigned` допустим только при `scoped: true`. Для одинаковой операции `all` имеет приоритет при объединении ролей. Области считаются отдельно: глобальное чтение заказов не расширяет право менять статусы назначенных заказов. Все направления позиций заказа должны входить в разрешённый набор. При переносе каталожной позиции проверяются исходное и новое направления.

## Каталог операций

| Привилегии | Область | Назначение |
| --- | --- | --- |
| `services.create`, `services.delete`, `services.reorder` | `all` | Создание, удаление и порядок направлений |
| `services.update` | `all` / `assigned` | Настройки направления и бронирования |
| `items.create`, `items.update`, `items.delete` | `all` / `assigned` | Товары и услуги; архивирование через `items.update` |
| `orders.read` | `all` / `assigned` | Рабочий список заказов |
| `orders.status`, `orders.schedule`, `orders.archive` | `all` / `assigned` | Статусы, предложение времени, архивирование |
| `calendar.read` | `all` / `assigned` | Календарь и фильтры, включая клиентов |
| `users.read`, `users.create`, `users.update`, `users.delete` | `all` / `assigned` | Аккаунты, с ограничениями ниже |
| `companies.read` | `all` | Список всех компаний и чтение данных компаний |
| `companies.manage` | `all` | Участники, распределение средств и журнал компаний |
| `topups.read`, `topups.confirm` | `all` | Заявки и подтверждение поступления средств |
| `companies.charge` | `all` / `assigned` | Списание по QR |
| `analytics.read` | `all` | Сводная аналитика |
| `settings.update` | `all` | Контакты комплекса |
| `roles.read`, `roles.create`, `roles.update`, `roles.delete`, `roles.assign` | Только защищённая роль администратора | Каталог и управление ролями/назначениями |

`roles.*` имеют `adminOnly: true`; включать их в пользовательскую роль нельзя (`400`). Защищённая роль администратора содержит все 28 привилегий с областью all; её привилегии нельзя изменить или удалить через API и обычные SQL-операции. Публичный каталог и контакты, личная корзина/заказы и права владельцев компаний сохраняют отдельные правила доступа.

## Защита от повышения доступа

Только администратор назначает роли. Делегированные users.create создают аккаунты без ролей. Делегированные users.update/delete не позволяют изменить аккаунт администратора, аккаунт с users.* / roles.* либо аккаунт с привилегией, которой нет у оператора. Области каждой привилегии также сравниваются: нельзя получить чужой расширенный доступ через смену пароля. Для assigned все направления управляемого аккаунта должны входить в назначения оператора; аккаунт без направлений недоступен. Для all обычные аккаунты без направлений доступны. Назначение ролей, даже пустого массива, неадминистратором возвращает 403.

Публичная регистрация не принимает роли, привилегии, назначения или состояние подтверждения телефона.

## Перенос существующих прав

Миграция 20261120040000_unified_roles создаёт защищённую роль администратора и обычные редактируемые роли «Менеджер» и «Сотрудник». При совпадении названия используется свободное название с числовым суффиксом; существующие пользовательские роли не изменяются и не переиспользуются. Назначения старых admin/manager/employee переносятся в UserAccessRole, пользовательские назначения сохраняются. Старый user не получает административных разрешений.

Исходные наборы привилегий менеджера и сотрудника записываются в RolePrivilege. В коде нет специальных проверок их названий или встроенных прав. Эти роли можно переименовывать, менять и удалять после снятия назначений. Удаление и изменение защищённой роли администратора возвращает 409.

## Профиль и совместимость

GET /auth/me, регистрация и вход возвращают accessRoles: [{role: {id, name, isAdministrator, grants}}], privileges: [{privilege, scope}] и serviceAssignments. CRUD пользователей возвращает роли и назначения. Для действий интерфейс проверяет privileges и области, для управления ролями — признак защищённой роли. Ответы и DTO не содержат role/userRole; старые поля в записи возвращают 400, а не игнорируются.

Права загружаются из БД на каждом защищённом запросе: изменения действуют со следующего запроса с существующим JWT. Уже выполняющийся запрос может завершиться с ранее проверенными правами. Новые JWT содержат только идентификатор и логин; старые JWT с любыми role claims не дают прав сверх актуальных назначений.

## Последний администратор

Удаление последнего администратора и снятие его роли через оба API пользователей возвращают 409. При полной замене сохраняются уже имеющиеся назначения: подтверждение прежнего набора ролей не удаляет и не создаёт заново последнего администратора.

Изменения ролей, аккаунтов и назначений сериализуются транзакционной блокировкой с повторной проверкой текущих прав инициатора. PostgreSQL-триггер на UserAccessRole и счётчик AdministratorState защищают от одновременного снятия ролей, удаления аккаунтов с каскадом, UPDATE назначений, массовых операций и отката транзакций. TRUNCATE аккаунтов/назначений при наличии администратора запрещён; TRUNCATE каталога ролей/привилегий ролей запрещён всегда. Привилегированный оператор БД, способный отключить триггеры или менять счётчик, находится за границей прикладной модели доступа.

Если администраторов изначально нет, доверенный оператор инфраструктуры назначает существующему аккаунту защищённую роль через UserAccessRole. Публичного самоназначения нет.

## Выпуск и проверки

Это несовместимое изменение схемы и DTO. Старый фронтенд и старый образ бэкенда требуют обновления: см. FRONTEND_AGENT_REQUIREMENTS.md и AUTH.md. Автоматический runner отказывает в переходе со старых колонок до согласованного выпуска; локальные проверки не означают деплой.

npm run test:e2e проверяет все HTTP/DB-сценарии на временной PostgreSQL 16. Дополнительный тест миграции сравнивает 5000 аккаунтов и 10000 позиций каталога, старые пользовательские роли/назначения, эффективные права каждого аккаунта и полный откат при ошибке зависимостей. Ролевые HTTP-тесты используют отдельную временную БД и проверяют конкурентный отзыв последнего администратора.
