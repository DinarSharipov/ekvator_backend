# Роли и привилегии

У аккаунта есть системный уровень `userRole` и несколько пользовательских ролей `AccessRole`. Роли объединяют разрешения на конкретные операции. Управление ролями и их назначение доступны **только системному администратору** (`userRole: admin`).

## API управления ролями

Все запросы требуют Bearer JWT администратора.

| Метод и путь | Результат |
| --- | --- |
| `GET /admin/privileges` | Каталог: `key`, `description`, `scoped`, `adminOnly` |
| `GET /admin/roles` | Список ролей с привилегиями |
| `GET /admin/roles/:id` | Одна роль |
| `POST /admin/roles` | Создание, `201` |
| `PUT /admin/roles/:id` | Полная замена названия, описания и привилегий, `200` |
| `DELETE /admin/roles/:id` | Удаление неназначенной роли, `204` |
| `PUT /admin/users/:id/roles` | Полная замена пользовательских ролей аккаунта, `204` |

Пример создания роли:

```json
{
  "name": "Оператор гостиницы",
  "description": "Заказы назначенных направлений",
  "grants": [
    { "privilege": "orders.read", "scope": "assigned" },
    { "privilege": "orders.status", "scope": "assigned" },
    { "privilege": "orders.schedule", "scope": "assigned" },
    { "privilege": "calendar.read", "scope": "assigned" }
  ]
}
```

Назначение через `PUT /admin/users/42/roles`: `{"roleIds":[1,2]}`. Пустой массив снимает все пользовательские роли; системный уровень сохраняется. `serviceTypeIds` задаются через `PUT /users/42`. Для гибкой роли без встроенных прав используйте `userRole: user`.

`grants` обязателен, пустой массив допустим. Повторять ключ нельзя. Название обрезается по краям, обязательно, до 100 символов; уникальность без учёта регистра. Описание необязательно, до 1000 символов; отсутствие в PUT очищает его. Неизвестные поля, ключи, области и повторяющиеся идентификаторы дают `400`. Несуществующие роли/пользователи — `404`; занятое название или удаление назначенной роли — `409`. Перед удалением снимите роль со всех пользователей.

## Области действия

- `all`: операция доступна для всех соответствующих ресурсов.
- `assigned`: операция ограничена направлениями из `serviceAssignments`; без назначений доступных направлений нет.

`assigned` допустим только при `scoped: true`. Для одинаковой операции `all` имеет приоритет при объединении ролей. Области считаются отдельно: глобальное чтение заказов не расширяет право менять статусы назначенных заказов. Все направления позиций заказа должны входить в разрешённый набор. При переносе каталожной позиции проверяются исходное и новое направления.

## Каталог операций

| Привилегии | Область | Назначение |
| --- | --- | --- |
| `services.create`, `services.delete`, `services.reorder` | `all` | Создание, удаление и порядок направлений |
| `services.update` | `all` / `assigned` | Настройки направления и бронирования |
| `items.create`, `items.update`, `items.delete` | `all` / `assigned` | Товары и услуги; архивирование через `items.update` |
| `orders.read` | `all` / `assigned` | Рабочий список заказов |
| `orders.status`, `orders.schedule`, `orders.archive` | `all` / `assigned` | Статусы, предложение времени, архивирование |
| `calendar.read` | `all` / `assigned` | Календарь и фильтры, включая клиентов |
| `users.read`, `users.create`, `users.update`, `users.delete` | `all` / `assigned` | Аккаунты, с ограничениями ниже |
| `companies.read` | `all` | Список всех компаний и чтение данных компаний |
| `companies.manage` | `all` | Участники, распределение средств и журнал компаний |
| `topups.read`, `topups.confirm` | `all` | Заявки и подтверждение поступления средств |
| `companies.charge` | `all` / `assigned` | Списание по QR |
| `analytics.read` | `all` | Сводная аналитика |
| `settings.update` | `all` | Контакты комплекса |
| `roles.read`, `roles.create`, `roles.update`, `roles.delete`, `roles.assign` | Только `admin` | Каталог и управление ролями/назначениями |

`roles.*` имеют `adminOnly: true`; включать их в пользовательскую роль нельзя (`400`). Администратор обладает всеми привилегиями независимо от назначенных ролей. Публичный каталог и контакты, личная корзина/заказы и права владельцев компаний сохраняют отдельные правила доступа.

## Защита от повышения доступа

Только администратор назначает системные уровни `admin`/`manager`, изменяет аккаунты с пользовательскими ролями и назначает сами роли. Делегированные `users.*` разрешают управление обычными пользователями и сотрудниками без пользовательских ролей. При `assigned` весь набор направлений управляемого аккаунта должен входить в набор оператора; аккаунт без направлений недоступен. При `all` обычные аккаунты без направлений доступны. Сотруднику обязателен непустой набор направлений.

Создание сотрудника также предоставляет встроенные права `employee`; учитывайте это при делегировании `users.create`/`users.update`. Публичная регистрация не принимает системные уровни, роли, привилегии или назначения.

## Совместимость и фронтенд

| Системный уровень | Встроенные права |
| --- | --- |
| `admin` | Все операции |
| `manager` | `items.*`, `orders.*`, `calendar.read`, `users.read/create/update`, `companies.charge` в назначенных направлениях; управление только сотрудниками |
| `employee` | `orders.read/status`, `calendar.read` в назначенных направлениях |
| `user` | Без встроенных административных привилегий |

Пользовательские роли добавляют права к встроенным. Для полностью настраиваемого набора используйте `user` с пользовательскими ролями.

`GET /auth/me`, регистрация и вход возвращают `accessRoles: [{role: {id, name, grants}}]`, `privileges: [{privilege, scope}]` и `serviceAssignments`. Интерфейс должен проверять эффективные `privileges`, а не только `userRole`. CRUD пользователей возвращает роли и назначения; эффективные права доступны в авторизационном профиле. Права загружаются из БД на каждом защищённом запросе: изменения действуют со следующего запроса с существующим JWT. Уже выполняющийся запрос может завершиться с ранее проверенными правами.

## Последний администратор

Удаление и понижение последнего администратора через `/users/:id` возвращают `409`. Изменения аккаунтов и назначений сериализованы транзакционной блокировкой; права инициатора повторно проверяются внутри транзакции. Одновременные понижения не оставляют систему без администратора.

Миграция `20261120030000_flexible_access_roles` добавляет каталог, роли, связи и PostgreSQL-триггеры. Счётчик `AdministratorState` и изменения администраторов обновляются атомарно, включая прямые SQL, массовые операции и откат. `TRUNCATE User` при наличии администратора запрещён. Привилегированный оператор БД, меняющий триггеры или сам счётчик, находится за границей прикладной модели доступа.

Миграция не создаёт аккаунты и не меняет существующие роли/пароли. Если администраторов не было, начальный аккаунт создаётся доверенным оператором инфраструктуры; публичного самоназначения нет.

## Проверка

`npm run test:access-roles` использует локальный `TEST_DATABASE_URL` с именем, заканчивающимся `_test`, создаёт отдельную временную БД, применяет миграции и удаляет БД после проверки. Проверяются HTTP-границы, объединение и отзыв привилегий, ограничения направлений, повышение доступа и конкурентная защита последнего администратора через HTTP и PostgreSQL. Подключению нужно право создания временной БД.
